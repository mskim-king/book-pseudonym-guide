고객번호·휴대폰 번호처럼 **같은 사람을 계속 구분해야 하는 식별자**는 지우는 대신 다른 값으로 바꿉니다. 이때 쓰는 것이 암호화·해시·토큰화입니다. 방법에 따라 되돌릴 수 있는지, 추측 공격에 강한지가 다르므로 목적에 맞게 골라야 합니다.

[TOC]

## 요약

- **일방향 해시는 키(솔트) 없이 쓰면 위험합니다.** 휴대폰 번호처럼 경우의 수가 적은 값은 모두 대입해 보면 원래 값을 알아낼 수 있습니다.
- 가명ID에는 **비밀 키를 쓰는 해시(HMAC)**나 **무작위 토큰 + 대응표**가 알맞습니다.
- 키와 대응표는 **추가정보**이므로 가명정보와 **분리 보관**합니다.

## 기법 비교

| 기법 | 되돌리기 | 같은 값 → 같은 결과 | 특징 | 쓰임 |
|---|---|---|---|---|
| 양방향 암호화 | 키가 있으면 가능 | 방식에 따라 | 키 유출 시 원본 노출 | 원본 복원이 꼭 필요할 때 |
| 일방향 해시 (키 없음) | 불가 (원칙) | 예 | **추측 공격에 취약** | 단독 사용 비권장 |
| 키 기반 해시 (HMAC, 솔트) | 키가 있어도 직접 복원은 불가 | 예 | 키를 모르면 대입 공격이 어려움 | 가명ID, 결합키 |
| 토큰화 (무작위 값 + 대응표) | 대응표가 있으면 가능 | 대응표 기준 | 값 자체에 정보가 없음 | 가명ID |
| 형태 보존 암호화 | 키가 있으면 가능 | 예 | 원래 형식(자릿수) 유지 | 기존 시스템 호환 |
| 순서 보존 암호화 | 키가 있으면 가능 | 예 | 크기 비교 가능 | 범위 검색 |
| 동형암호 | 키가 있으면 가능 | 방식에 따라 | 암호화한 채로 계산 | 04-8 참고 |

## 왜 "키 없는 해시"가 위험한가

```text
휴대폰 번호 010-XXXX-XXXX → 가능한 값은 약 1억 개
SHA-256("010-2345-6789") = (공개된 해시값)
→ 공격자가 1억 개를 모두 해시해서 비교하면 원래 번호를 찾을 수 있음
```

비밀 키를 섞은 HMAC은 **키를 모르면 이런 대입이 불가능**합니다. EU 개인정보보호이사회(EDPB)의 2025년 가명처리 지침 초안도 되돌릴 수 있는 암호화보다 HMAC 같은 **일방향 키 기반 함수**를 권하는 것으로 소개되었습니다. (09-1)

## 예제: HMAC으로 가명ID 만들기

`code/01_techniques.py`

```python
import hashlib, hmac
SECRET_KEY = b"demo-secret-key-keep-separately"   # 실제로는 별도 보관(추가정보)

def pseudonym(value: str) -> str:
    return "P-" + hmac.new(SECRET_KEY, value.encode(), hashlib.sha256).hexdigest()[:8]
```

**실행 결과 (일부)**

```text
{'가명ID': 'P-04fc5cd2', '연령대': '40대', '성별': '남', '지역': '062**', ...}
{'가명ID': 'P-4d0d8cf5', '연령대': '40대', '성별': '여', '지역': '062**', ...}
```

같은 휴대폰 번호는 항상 같은 가명ID가 되므로, 이름 없이도 **같은 고객의 기록을 이어서 분석**할 수 있습니다.

[[TIP("요령: 목적별로 다른 키 쓰기")]]

모든 프로젝트에 같은 키를 쓰면, 서로 다른 프로젝트의 가명정보를 가명ID로 이어 붙일 수 있게 됩니다. **프로젝트(제공처)마다 다른 키**를 쓰고, 키는 정기적으로 교체 계획을 세우세요.

[[/TIP]]

## 실무 체크포인트

- [ ] 키 없는 일방향 해시를 단독으로 쓰지 않았는가
- [ ] 키·대응표를 가명정보와 분리 보관하는가
- [ ] 프로젝트마다 다른 키를 쓰는가
- [ ] 키 접근 권한과 교체 주기를 정했는가
